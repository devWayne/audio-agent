# 性能、计算成本与测量边界

[文档目录](README.md) · [模型配置](models.md) · [使用指南](user-guide.md)

2026-10-24，当前 Mac 实际为 **M1 Pro、10 核 CPU、16 GiB 内存**。M4 Max 未纳入实测，以下不代表其运行结果。

## 75 秒生产观察

19:32:22–19:33:37（Asia/Shanghai），保持已有内置麦克风监听、Silero VAD、中文转写和自动说话人分析设置。没有为采样切换模式或启动额外推理。记录只保存在忽略的 `.data/performance/observed-20261024T113222Z*.json`，没有上传录音或转写。

| 项目 | 实际结果 | 解释 |
| --- | --- | --- |
| 常驻 Web/VAD | 平均 21.75% 单核 CPU，RSS 55–58 MiB | 由窗口前后累计 CPU 时间差计算；此窗口包含发声，并非纯静音基准 |
| 采音 ffmpeg | 平均 3.44% 单核 CPU，RSS 22–23 MiB | 监听持续运行 |
| 原生菜单栏 | 平均 0.11% 单核 CPU，RSS 71 MiB 左右 | 不含 Web 控制台所在浏览器进程 |
| Whisper ASR | 9 段、33.044 秒音频；worker 墙钟耗时总计 19.158 秒，中位 2.068 秒/段 | 每段 1.860–2.455 秒，包含启动和加载；不是 CPU 使用率 |
| ASR 内存 | 一秒采样看到 RSS 峰值 2018.84 MiB，约 1.97 GiB | 采样峰值，不保证捕获瞬时峰值；RSS 不等于完整 Metal/统一内存占用 |
| 自动说话人 | 9 项完成，模型分析耗时共 3.035 秒 | 部分录音未检出有效说话人；完成不等于身份准确 |
| 积压与交换 | 待处理最高 1、结束 0；swap 用量约 821.81 MiB 前后不变，无新增 swapout | 只证明这段观察没有持续积压，不是全天稳定性或电量测试 |

macOS 进程 CPU 的 **100% 约表示占用一个 CPU 核**。三类常驻进程合计约 25.3% 单核，即 0.253 核；不能把它说成整台机器损失 25% 性能，也不能以除以 10 的结果预测前台应用实际变慢多少。ASR 和说话人短进程退出前的部分 CPU 时间会漏采，不能拿采样总和作为完整推理 CPU 成本。观察器每秒额外执行两个只读状态请求，也有少量开销。

本次仅取得全系统 GPU 计数，没有可靠的 Audio Agent 独占 GPU 占用和功耗数据，因此不报告应用 GPU 百分比、瓦数或电池续航损失。不能把不同进程 RSS 相加当作统一内存总占用。

## 开销来自哪里

- **停止监听**：没有采音、VAD 或新 ASR。后台服务与菜单栏还在；停止后已排队的任务可继续收尾。此次没有专门测量停止状态。
- **开启监听、安静**：持续采音并检查音量和 VAD。没有新语音片段时不触发 ASR，安静环境下通常比持续发声轻，但仍有基础占用。
- **发声后转写**：复用 Handy 的 `ggml-large-v3-q5_0.bin`，文件约 1.081 GB，whisper.cpp 默认 4 CPU 线程并启用 Metal GPU。每段启动独立 worker，完成后退出，因而短句也付出模型加载的固定成本，不是一直把大模型留在服务进程中。
- **说话人分析**：本地 sherpa-onnx CPU，默认 2 线程；与 ASR 共用推理锁，优先完成转写，之后补说话人标签。不开并行重推理以避免争抢，但繁忙时标签可能延后。
- **MCP 只读拉取**：读取已有文本和标签，不重新识别、不打开麦克风；客户端调用转写工具才另外运行模型。

## M1 Pro 与 M4 Max 的选择

当前 M1 Pro 在这段真实短句负载中能跟上。轻办公时可保留自动转写与自动说话人；进行剪辑、3D、编译或其他本地模型推理时，它们会竞争 CPU、GPU 与统一内存。电视和旁人讲话若不断触发 VAD，就会持续增加推理次数，单纯保持“开启”无法代表低负载。

M4 Max 有 14/16 核 CPU、32/40 核 GPU、410/546 GB/s 内存带宽，资源余量更大；当前实现没有使用 Neural Engine。其具体改善倍数、耗电与是否影响其他工作须在那台机器测量，不能用核心数或带宽直接换算。MacBook Pro 的 M4 Max 标配为 36 GB，另有 48/64/128 GB，具体配置应通过目标机器的「关于本机」核对。[Apple 官方规格](https://support.apple.com/en-us/121554)

本地 ASR 没有按分钟的云端 API 费用，成本是本机算力、发热和耗电。若无需每段都有文字，按需识别可减少总工作量；若最终仍处理全部录音，仅延后不代表更省。本次观察没有为测试改变正在运行的转写与说话人设置。

## 硬件损耗和使用寿命

正常散热条件下，这属于 CPU/GPU 的常规计算负载，不能把“占用 25% 单核”理解成“硬件损耗 25%”或“寿命缩短 25%”。Apple 说明 Mac 正常使用中发热是正常现象，温度传感器和风扇负责冷却关键部件；本次没有测温或进行长期寿命试验，因此不能给出寿命百分比。[Apple 温度说明](https://support.apple.com/en-us/102336)

更直接的长期成本是电池：持续推理增加耗电，电池供电时会更快累计使用量和充电循环，电池容量随使用逐渐衰减。额外减少多少续航、加快多少老化，目前没有受控功耗测量，不能量化。[Apple 电池循环说明](https://support.apple.com/en-us/102888)

录音也会写 SSD：16 kHz、单声道、PCM16 的音频本体约 115.2 MB/小时有效音频；8 小时连续有效音频约 921.6 MB，临时副本、数据库和系统交换另计。静音不持续落盘。这是数据量估算，不是 SSD 寿命测试，也不能用它推算具体损耗率。

接入 Codex/Claude Code 后，读取的转写成为该客户端的模型上下文，其 token/额度按客户端计费方式计算；这与本地 ASR 免费是两件事。建议增量读取而非每次重复读取全部历史，配置见 [MCP 接入](mcp-integration.md)。


## 三项分开看：纯 VAD 微基准

2026-10-24 19:59（Asia/Shanghai）在同一台 M1 Pro 上单独测量现有 Silero-v4：公开 JFK 音频重复至 60 秒，以及 60 秒数字静音，每种一次；每次 1875 个 512-sample 帧。只计 probability 调用的进程 CPU 时间，初始化、WAV 解码和预分帧单独排除，没有打开麦克风或改动生产设置。

- 60 秒语音：0.209640 CPU 核秒，折算实时约单核 0.349%。
- 60 秒静音：0.208545 CPU 核秒，折算实时约单核 0.348%。
- 首次初始化：墙钟 0.075736 秒、CPU 0.070653 核秒，含依赖导入/session创建/验证帧。

数据在 `.data/performance/vad-isolated.json`。这是单次、离线跑满的纯模型基准，频率与调度可能不同于常驻运行；不能据此预测电量。它明确说明之前整个 Web/VAD 进程的 21.75% 单核 CPU 不能都归给 VAD；采音、状态/文档请求、标签注释与刷新等另有开销。

当前优先优化的是 Whisper 转写的 GPU/内存与重复启动成本。说话人分析是追加的 CPU 工作；匹配已登记参考及显示名字/备注不重新运行 ASR。VAD 本身轻，关闭它还可能增加非语音触发的后续重推理。三项开启时 VAD 持续运行，ASR 与 speaker 按需串行处理已完成声段；安静且队列清空时这两类重推理均不运行。各项处理时间口径不同，不能将 19.158 秒与 3.035 秒直接换算成电耗比例。


## 复测建议

在目标机器分别记录停止监听、安静监听、固定公开语音负载三种状态；保持相同模型、线程、设备、片段长度和浏览器刷新方式。分别记录累计 CPU 时间、墙钟时长、内存采样、队列积压与交换量。电池与 GPU 功耗需要独立受控测量，不能从上述耗时直接推算。此报告只包含一次短时观察，原始本机采样位于 Git 忽略的 `.data/`，不随公开仓库分发。
